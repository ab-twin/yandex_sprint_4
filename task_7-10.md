# Задание 7 — Шардирование данных

---

## Общие принципы выбора шард-ключей

При проектировании схемы данных для MongoDB и выборе шард-ключей используются следующие критерии:

* **Кардинальность**: значений должно быть много → равномерное распределение.
* **Низкая вероятность “горячего” шарда**.
* **Иммутабельность**: шард-ключ должен быть неизменяемым.
* **Targeted-queries**: чтобы частые операции попадали в один конкретный шард.
* **Баланс между insert-нагрузкой и query-нагрузкой**.

---

# Коллекция `products`

## Предлагаемая схема коллекции

```json
{
  "_id": "ObjectId",
  "sku": "String",
  "name": "String",
  "category": "String",
  "price": "Number",

  "stock_by_zone": {
    "msk": Number,
    "spb": Number,
    "ekb": Number,
    "kld": Number
  },

  "attributes": {
    "color": "String",
    "size": "String"
  },

  "created_at": "Date",
  "updated_at": "Date"
}
```

### Основные индексы:

```js
db.products.createIndex({ category: 1, price: 1 });
db.products.createIndex({ sku: 1 }, { unique: true });
```

---

## Выбор стратегии шардирования

### **Шард-ключ**:

```json
{ "_id": "hashed" }
```

### **Причины выбора:**

* `_id` — случайный и неизменяемый → идеален для hashed-шардирования.
* Вставки распределяются по шардам равномерно.
* Частые обновления остатков также равномерно распределены.
* Карточка товара (`GET /product/:id`) всегда ищется по `_id` → targeted-query.

### Команда MongoDB:

```js
sh.enableSharding("mobile_store");

sh.shardCollection(
  "mobile_store.products",
  { _id: "hashed" }
);
```

# Коллекция `orders`

## Схема коллекции

```json
{
  "_id": "ObjectId",
  "customer_id": "ObjectId",
  "created_at": "Date",

  "status": "String",
  "total_amount": "Number",
  "geo_zone": "String",

  "items": [
    {
      "product_id": "ObjectId",
      "name": "String",
      "category": "String",
      "price": "Number",
      "quantity": "Number"
    }
  ],

  "updated_at": "Date"
}
```

### Основные индексы:

```js
db.orders.createIndex({ customer_id: 1, created_at: -1 });
db.orders.createIndex({ geo_zone: 1, status: 1, created_at: -1 });
```

---

## Выбор стратегии шардирования

### **Шард-ключ:**

```json
{ "customer_id": "hashed" }
```

### **Обоснование:**

* Создание заказа всегда известно по `customer_id` → запись идёт в нужный шард.
* История заказов (`find({ customer_id })`) — targeted-query.
* Много пользователей → равномерная нагрузка.
* Статусы заказа запрашиваются тоже по пользователю.

### Команда MongoDB:

```js
sh.enableSharding("mobile_store");

sh.shardCollection(
  "mobile_store.orders",
  { customer_id: "hashed" }
);
```

# Коллекция `carts`

Корзины — самая динамичная коллекция с частыми апдейтами, большим количеством гостевых сессий и TTL очисткой.

---

## Схема коллекции

```json
{
  "_id": "ObjectId",

  "user_id": "ObjectId|null",
  "session_id": "String|null",

  "owner_key": "String",   // user_id.toString() или session_id — никогда не меняется

  "items": [
    {
      "product_id": "ObjectId",
      "quantity": "Number"
    }
  ],

  "status": "String",       

  "created_at": "Date",
  "updated_at": "Date",
  "expires_at": "Date"      
}
```

### TTL-очистка:

```js
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });
```

### Основные индексы:

```js
db.carts.createIndex({ owner_key: 1, status: 1 });
db.carts.createIndex({ user_id: 1, status: 1 });
db.carts.createIndex({ session_id: 1, status: 1 });
```

---

## Выбор стратегии шардирования

### **Шард-ключ:**

```json
{ "owner_key": "hashed" }
```

### Почему именно так:

* Корзина всегда принадлежит либо пользователю, либо гостевой сессии → мы знаем ключ.
* `owner_key` **никогда не меняется**, чего требует MongoDB.
* Все операции (получение текущей корзины, добавление товара, обновление) — targeted и идут в один шард.
* Огромное количество уникальных сессий → очень хорошая кардинальность → отличное распределение нагрузки.
* TTL удаление работает на каждом шарде независимо → тоже хорошо.

### Команда MongoDB:

```js
sh.enableSharding("mobile_store");

sh.shardCollection(
  "mobile_store.carts",
  { owner_key: "hashed" }
);
```

---

Сводная таблица по шард-ключам

| Коллекция    | Шард-ключ     | Тип      | Почему                                                                                 |
| ------------ | ------------- | -------- | -------------------------------------------------------------------------------------- |
| **products** | `_id`         | `hashed` | Хорошее распределение, частые обновления, точечные GET по `_id`.                       |
| **orders**   | `customer_id` | `hashed` | История заказов по пользователю, targeted insert/read, распределение по пользователям. |
| **carts**    | `owner_key`   | `hashed` | Корзина по владельцу, targeted-queries, ключ неизменяем, высокая кардинальность.       |

---

# Итог

Проектирование схем и выбор стратегий шардирования выполнены так, чтобы обеспечить:

* равномерное распределение данных;
* targeted-запросы по ключевым операциям;
* масштабируемость для высоких нагрузок;
* минимизацию горячих шардов;
* соответствие бизнес-сценариям магазинов.

# Задание 8 — Выявление и устранение «горячих» шардов в MongoDB

### **Метрики мониторинга hot shard:**

| Уровень  | Метрики                                       |
| -------- | --------------------------------------------- |
| Shard    | CPU, Disk I/O, Latency, Data size, opcounters |
| Mongos   | routed ops, latency per op type               |
| Business | количество запросов по категориям, ошибкам    |

---

### **Способы устранения hot shard:**

| Стратегия           | Эффект                                |
| ------------------- | ------------------------------------- |
| Hashed шард-ключи   | равномерное распределение             |
| Composite keys      | баланс с сохранением фильтрации       |
| Resharding          | исправление плохого ключа без простоя |
| Балансировка чанков | выравнивание данных                   |

| Добавление шардов   | увеличение мощности кластера          |
| Правильные индексы  | уменьшение количества сканирований    |

# Задание 9 — Настройка чтения с реплик и консистентность

MongoDB Replica Set позволяет читать данные как с primary (strong consistency), так и с secondary (eventual consistency, задержка репликации возможна).
Для интернет-магазина критично не допускать:

* продажу товара, которого нет в наличии
* отображение неверного статуса заказа
* потери содержимого корзины

Поэтому чтение с secondary допускается только там, где это безопасно.

---

## Таблица: операции чтения — Primary или Secondary


| Коллекция    | Операция                                        | Primary | Secondary | Почему                                                                          |
| ------------ | ----------------------------------------------- | ------- | --------- | ------------------------------------------------------------------------------- |
| **products** | Поиск товаров по категории и цене               | ❌       | ✔️        | Лёгкое чтение, допустима небольшая задержка, данные почти не меняются           |
| **products** | Просмотр страницы товара (`GET /products/:id`)  | ❌       | ✔️        | Описание товара редко меняется, eventual consistency приемлема                  |
| **products** | Получение остатка товара в геозоне              | ✔️      | ❌         | Если читать со secondary → риск продать товар, отсутствующий по факту           |
| **orders**   | История заказов пользователя                    | ✔️      | ❌         | Нельзя показывать устаревший список: статус может поменяться секунду назад      |
| **orders**   | Просмотр статуса заказа                         | ✔️      | ❌         | Критично для клиента — должен видеть текущий статус («оплачен/доставляется»)    |
| **orders**   | Админские аналитические отчёты                  | ❌       | ✔️        | Данные условно stale не мешают аналитике                                        |
| **carts**    | Получение текущей корзины по user_id/session_id | ✔️      | ❌         | Если корзина читается со secondary, клиент может видеть устаревшие товары       |
| **carts**    | Просмотр корзины на гостевой сессии             | ✔️      | ❌         | Данные часто обновляются, риск рассинхронизации                                 |
| **carts**    | Аналитика по брошенным корзинам                 | ❌       | ✔️        | Stale-данные допустимы, аналитические отчёты не требуют строгой консистентности |

---

## Допустимая задержка репликации

MongoDB replication lag (`replicationLag`) может быть:

* в норме: **0–100 мс**
* допустимо для eventual-read: **до 1 секунды**
* критично: **> 5 секунд** — может вызвать устаревшие данные на витрине

### Рекомендации по задержкам:

| Тип операции               | Допустимая задержка secondary |
| -------------------------- | ----------------------------- |
| Поиск товаров по категории | до **1–2 секунд**             |
| Описание товара            | до **2 секунд**               |
| Аналитика (orders, carts)  | до **30–60 секунд**           |
| Запрос статуса заказа      | **0 секунд** (только primary) |
| Данные корзины             | **0 секунд** (только primary) |
| Остатки товаров            | **0 секунд** (только primary) |

---

## Обоснование решения

---

## Коллекция `products`

### Можно читать с **secondary**:

* Поиск товаров по категории, фильтры по цене
* Страница товара

**Почему:**

* товары меняются редко
* небольшая задержка (1–2 секунды) не критична
* огромный объём чтения → перенос нагрузки на secondary снижает давление на primary

### Только **primary**:

* остатки товаров (`stock_by_zone`)

---

## Коллекция `orders`

### Только **primary:**

* история заказов клиента
* просмотр статуса заказа

**Почему:**

* статус может меняться (оплата, сборка, доставка)
* нельзя показывать пользователю «заказ всё ещё в обработке», когда он уже отправлен
* требования strong consistency

### Можно читать с **secondary:**

* отчёты / аналитика по заказам
* агрегированные показатели

---

## Коллекция `carts`

### Только **primary:**

* получение текущей корзины
* операции над корзиной
* guest → user merge
* изменение количества товара
* удаление товара

**Почему:**

* корзина — самый динамичный объект в магазине
* задержка даже в 500 мс может привести к:

    * пользователь удалил товар → но видит его снова
    * конфликт слияния корзин
    * заказ создаётся с устаревшей корзиной

### Secondary только для аналитики (брошенные корзины)

* аналитика abandoned carts
* тренды, отчёты

# ЗАДАНИЕ 10 — Миграция на Cassandra для высоконагруженного интернет-магазина

Cassandra выбирается из-за:

* **лидерless-репликации** (нет единой точки отказа, легко масштабируется)
* **линейного масштабирования** (каждый новый узел повышает пропускную способность)
* **отсутствия глобального решардинга при добавлении узлов**, как в MongoDB
* **распределения данных через consistent hashing**
* **высокой скорости записи**

---

# Какие данные критичны и подходят для Cassandra

| Сущность                      | Важность      | Задержки                   | Частота записи | Подходит для Cassandra?                        | Причины                                                      |
| ----------------------------- | ------------- | -------------------------- | -------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| **Orders (заказы)**           | высокая       | важна актуальность статуса | высокая        | ✔ Да                                           | Записи append-only, огромное количество при высокой нагрузке |
| **Products (товары)**         | средняя       | не критичны задержки       | средняя        | ✔ Да (частично)                                | Каталожные данные хорошо ложатся в wide-row модель           |
| **Carts (корзины)**           | очень высокая | нужна консистентность      | очень высокая  | ❓ Частично                                     | Нужна strong consistency → Cassandra может, но с CL=QUORUM   |
| **User sessions**             | низкая        | не критично                | очень высокая  | ✔ Да                                           | Отличный кандидат (TTL, быстрые записи)                      |
| **Order history per user**    | высокая       | критично                   | средняя        | ✔ Да                                           | Хорошо ложится в wide partition                              |
| **Real-time остатки товаров** | критично!     | очень важно                | высокая        | ❌ Лучше оставить в Redis или в Mongo с primary | Cassandra не даёт strong absolute consistency по умолчанию   |

# Модель данных Cassandra + ключи

## Orders — горячие записи под высоким трафиком

Цель:

* Скорость записи 50k ops/s
* Быстрый доступ к заказам пользователя
* Без горячих партиций

### Partition key: `customer_id`

### Clustering key: `created_at DESC`

```cql
CREATE TABLE orders_by_user (
    customer_id UUID,         -- partition key
    created_at TIMESTAMP,     -- clustering key
    order_id UUID,
    status TEXT,
    total_amount DECIMAL,
    geo_zone TEXT,
    items LIST<FROZEN<item>>,
    PRIMARY KEY ((customer_id), created_at)
) WITH CLUSTERING ORDER BY (created_at DESC);
```
---

## Order lookup по order_id - быстрый доступ

Дополнительно нужна таблица:

```cql
CREATE TABLE order_by_id (
    order_id UUID PRIMARY KEY,
    customer_id UUID,
    created_at TIMESTAMP,
    status TEXT,
    total_amount DECIMAL
);
```

---

## Product catalog

Запросы:

* Все товары категории
* Фильтр по цене
* Просмотр карточки товара

## Partition key: `category`

## Clustering key: `price`, `product_id`

```cql
CREATE TABLE products_by_category (
    category TEXT,
    price DECIMAL,
    product_id UUID,
    name TEXT,
    attributes MAP<TEXT, TEXT>,
    PRIMARY KEY ((category), price, product_id)
) WITH CLUSTERING ORDER BY (price ASC, product_id ASC);
```

---

## User sessions

* TTL
* миллионы записей
* высокая частота обновлений
* геораспределение

```cql
CREATE TABLE sessions (
    session_id UUID PRIMARY KEY,
    user_id UUID,
    created_at TIMESTAMP,
    last_seen TIMESTAMP
) WITH default_time_to_live = 604800;  -- 7 days
```

## Стратегии целостности в Cassandra

Cassandra не реализует strong consistency по умолчанию.
Нам нужно выбрать стратегию **под каждую сущность**.

---

## Hinted Handoff

* Быстрое восстановление узлов после кратковременного сбоя
* Отлично подходит для **session**, **products**

### Применяем к:

| Сущность         | Причина                               |
| ---------------- | ------------------------------------- |
| sessions         | допускают eventual consistency        |
| products         | каталожные данные не критичны         |
| orders (вставка) | запись всегда идёт в пару узлов сразу |

---

## Read Repair

Исправление расхождений во время чтения.

* Подходит, когда **частые чтения + важна корректность**
* Баланс между скоростью и консистентностью

### Применяем к:

| Сущность             | Причина                                      |
| -------------------- | -------------------------------------------- |
| orders_by_user       | важно, чтобы история заказов была корректной |
| products_by_category | мониторинг каталога                          |

---

## Anti-Entropy (Repair / Reaper)

Глобальный repair кластера (раз в сутки/неделю):

* дорогостоящая операция
* нужна для сильной целостности
* применяется для **критичных данных**

### Применяем к:

| Сущность    | Причина                            |
| ----------- | ---------------------------------- |
| orders      | критичная бизнес-информация        |
| order_by_id | данные должны совпадать во всех DC |

---

# Выбор уровня согласованности (Consistency Level)

| Сущность         | Read CL      | Write CL | Причина                  |
| ---------------- | ------------ | -------- | ------------------------ |
| orders           | QUORUM       | QUORUM   | целостность              |
| order history    | LOCAL_QUORUM | QUORUM   | доступ + консистентность |
| products         | ONE          | QUORUM   | быстрые чтения           |
| sessions         | ONE          | ONE      | максимальная скорость    |
| analytics events | ONE          | ANY      | огромная скорость записи |
